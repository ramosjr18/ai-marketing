# ai-marketing

A prompt framework, versioned in git, that turns one company into a marketing brain: who the
company is, what it sells and at what price, who buys it, and how it speaks. Markdown is the
execution layer; an agent (Claude Code, Codex, Cursor...) runs it. Code appears only where an
agent cannot reach: fetching, parsing, rendering.

One company per repo. Clone it, run `/setup`, and the blueprint it writes is yours and stays on
your machine: everything the commands generate is gitignored.

## How it works

1. **Blueprint** — `.claude/skills/company-blueprint/0*.md` (company level, `02`/`05`/`07`/`08`
   are indexes) plus one folder per sellable unit in `offering/<slug>/` (`unit.md`, `icp.md`,
   `competitors.md`, `pricing.md`). Generated by the commands below, **gitignored**. The
   templates under `templates/` are what ships. `CLAUDE.md` imports the one-screen overview so
   every session starts knowing the company.
2. **Commands** — `.claude/commands/*.md`. Each is a procedure the agent follows: it reads the
   blueprint, asks the owner one question at a time (closed questions as selectors), searches
   the web only with sources, and writes nothing without explicit approval.
3. **Source material** — `documents/` (decks, product sheets, brand assets, bank statements),
   gitignored except its README.

Start: `/setup`. Then follow the build order at the end of this file.

## Commands

| Command | What it produces | Reads | State |
|---|---|---|---|
| `/setup` | `00-overview` · `01-company` · `02-offering` (index) + `offering/<slug>/unit.md` · `03-people` · `04-voice` | website, `documents/`, interview | stable |
| `/costs` | `06-costs` — cost per billable hour, capacity, overhead (internal) | `03-people`, `02-offering` | stable |
| `/icp` | `offering/<slug>/icp.md` per unit (or `_shared/` per group) + index `07-icp` — ideal customer, per market | `02-offering`, `05-pricing` | stable |
| `/price-it` | `offering/<slug>/pricing.md` per unit + `05-pricing` aggregated rate card with floors; updates `02-offering` prices | `06-costs`, `07-icp`, `08-competitors`, past sales | stable |
| `/competitors <unit\|prompt>` | `offering/<slug>/competitors.md` per unit + index `08-competitors` — who, what, published prices, price band per market, positioning gap, objection map, alerts; one subagent per product or service | `07-icp`, `02-offering`, `05-pricing`, `04-voice` | stable |
| `/product <unit> [<section>]` | `offering/<slug>/product.md` + `hallazgos.md` — what the unit **really is past the category it falls into**, capability by capability with the work each one removes, how to tell it in one line / three / a demo, what it is compared against, and **what can be demonstrated today**. Non-linear: the owner picks the sources each run and can skip the interview. Findings go to `hallazgos.md`, written so somebody else can reproduce them | `unit.md`, `icp.md`, `documents/products/`, the app via `tools/peek.py` | stable |
| `/set-engine` | prepares the machine: checks Go, the sending engine, `imap-tools` and the shared infra, names what it would install and under which licence, installs on approval, picks Postgres or SQLite, writes the engine block of `.env` | `01-company`, the machine | stable |
| `/set-mail` | outreach identity: sending address, SMTP/IMAP into `.env`, signature, regional variant of the language, personal tone → `tone/<slug>.md`, daily cap, and **deliverability verified live** → `03-people` outreach block | `03-people`, `04-voice` | stable |
| `/mailbox [add\|list\|check] <slug>` | adds, lists and checks the mailboxes outreach is sent from: credentials into `.env` under `MAILBOX_<SLUG>_*`, registered in the engine by reference, login tested. Lighter sibling of `/set-mail` for a second mailbox on a verified domain | `.env`, `03-people` | stable |
| `/prospects <unit> [market] [n]` | `offering/<slug>/prospects.csv` + `prospects-runs.md` — real companies matching the unit's ICP, one verifier per candidate, verified buying signal with URL, public email or LinkedIn route. Discovery in two phases (candidates → evidence); no evidence, no row | `offering/<slug>/icp.md`, `unit.md`, existing rows, `_shared/suppression.csv` | stable |
| `/campaign [<unit>\|"<prompt>"\|close <slug>]` | a campaign belongs to one unit and has **one objective**, so a product can have several: trial signups, a launch in a second market, reactivating the silent. Defines the ICP slice, the angle and the mailbox, and assigns prospects explicitly — **one prospect, one active campaign** | `unit.md`, `icp.md`, `03-people`, `prospects.csv` | stable |
| `/outreach <unit> [--limit N\|--dry\|--linkedin]` | turns verified prospects into a campaign in the engine: **one email written whole per prospect** from its verified evidence, not a template with a variable; **every email shown rendered** in batches of five before approval; campaign left activated but unsent. `--linkedin` drives the browser channel. Step 5b learns the tone from the review | `campaign.md`, `prospects.csv`, `product.md`, `icp.md`, `03-people`, `04-voice`, `tone/<slug>.md` | stable |
| `/mail-sync [--days N\|<unit>]` | reads the mailboxes over IMAP (`tools/imap_fetch.py`), matches each message to a prospect by thread, address or domain, classifies the answer with the sentence that proves it, and proposes the changes to `prospects.csv`, `events.csv` and `suppression.csv`. Never replies, never marks as read | `prospects.csv`, `events.csv`, `.env` | stable |
| `/adjust-tone [<slug>] ["<instruction>"]` | turns a real correction into a tone rule in `tone/<slug>.md`, deciding whether it is personal or brand, refusing to stack contradictions and capping the list at 10. **Mostly runs by itself**: `/outreach` Step 5b proposes what the review taught, without being asked | `tone/<slug>.md`, `03-people`, `04-voice` | stable |
| `/client [<anything>]` | opens a client case under `clients/<slug>/` and brings its material in. **No single way in**: an audio file, a transcript pasted into the chat, a PDF, a URL, a name, or a key from `prospects.csv`. Audio is transcribed locally (`tools/transcribe.py`), each conversation becomes `transcripts/<uuid7>.md` and each one gets a `summaries/<uuid7>.md`: the problem in one sentence, what was discussed, **the figures with the minute they were said at**, and **what was promised out loud**. The case can be born without a client and be renamed or merged later. `research <slug>` studies the company itself and writes five files — who they are, what they did before with outsiders, what is said about them, how they decide and buy, who signs — fanning out one search per axis, source and date on every line, contradictions left visible. `email <slug>` drafts the case's correspondence and **never sends**: `confirm` reads the Sent folder over IMAP and stores the version that actually went out, because what leaves is often not what was written | the material, `prospects.csv`, `04-voice` | stable |
| `/diagnose <slug> [<process>]` | `clients/<slug>/diagnostico.md` + `preguntas.md` — the four-step method the rate card is built on, over one to three processes: measure frequency, duration, people and errors → cost today against saving → failure signals → verdict. **Every figure carries its provenance**, and "not worth it" is a valid outcome written with the same care as a yes | the case, the unit's `pricing.md` and `unit.md` | stable |
| `/propose <slug> [<type>]` | `clients/<slug>/proposals/YYYY-MM-DD-<type>.md` in one of four registers: **note** (someone close, no price, but the scope in writing), **diagnosis** and **project** (rate-card price only), **programme** (no price, but the deal written out). Seven gates run before a line is written: no price over an unconfirmed figure, no invented terms, and what was promised on a call binds what gets written | `diagnostico.md`, `preguntas.md`, `05-pricing`, `unit.md`, `04-voice`, `03-people` | stable |
| `/calendar-sync` | the outreach calendar as a view: what goes out when, and what is already booked | `prospects.csv`, `events.csv`, the calendar | stable |
| `/export [<unit>]` | packages what the repo knows so it can be carried to another machine or another person. Two questions, **neither with a default**: how much, and **who for** — that second one is a security boundary, since `.env`, the engine database and `.peek/` never travel to a teammate. `suppression.csv` travels **always**, at every scope: handing over the repo without it hands over the ability to write to people who asked not to be. Produces a dated folder with a README that says what is missing, not only what is there | the whole blueprint | stable |
| `/value-case` | reference client case: what the problem costs them today → value method for `/price-it` | `07-icp`, `06-costs` | planned |
| `/setup-update` | re-reads website + `documents/`, diffs against the blueprint, batch approval, changelog. Closes `/setup` gaps | `01`-`04` | planned |
| `/analyze <item\|prompt>` | is it working? Reads what the other commands produced and what happened since (sales, replies, outcomes) and says where the blueprint, the ICP or the price fell short, with evidence. Takes an item name or a free question | everything under `0*.md`, the trackers | planned |

## The sending engine

`/outreach` does not send. It writes the emails, shows them rendered, and leaves a campaign
activated in a **separate engine** that this repo neither ships nor vendors.

`/set-engine` walks that install. It points at [cold-cli](https://github.com/andersmyrmel/cold-cli)
(MIT, Go, builds from source), names the licence of everything it would put on the machine, and
asks before touching anything. For cold outreach the upstream needs three changes: send
`multipart/alternative` instead of HTML only, append a signature to each part, and lay out
paragraphs with a max width instead of `<br>`. **That fork is yours to make**: clone it, patch
it, build it, and point `COLD_CLI_BIN` at your binary. This repo distributes no fork and
maintains none, and it runs unpatched too, with HTML-only emails and no signature on the text
part.

What never leaves this repo in any case: `.env`, the engine's database, and anything under
`clients/`.

## Outreach state

State lives inside the blueprint, gitignored with it: `offering/<slug>/prospects.csv` (one row
per prospect, status and next touch), `offering/<slug>/prospects-runs.md`,
`offering/<slug>/drafts/`, and company-wide `offering/_shared/events.csv` and `suppression.csv`.
Columns and statuses: `templates/offering/README-outreach.md`.

`suppression.csv` is the one file that travels at every export scope. A repo handed over without
it hands over the ability to write to people who asked not to be written to.

## Adding a command

A new file under `.claude/commands/` is picked up when a session starts. In the session that
created it, the slash command is not registered yet: run it by reading the file and following
it, or restart the session.

## Rules every command follows

- **One question per message.** Closed questions are selectors; "don't know", "skip", "later"
  always valid. Long static questionnaires exhaust people.
- **Propose, then write.** Nothing touches a blueprint file without an explicit yes.
- **Nothing invented.** Every figure is `[stated]` by the owner, `[inferred from product]`, or
  `[Benchmark]` with URL and year. Salaries, margins and market sizes are searched, never
  recalled from model memory.
- **Internal stays internal.** Costs, floors, margins, real client names: never quoted outside.
- **Generic.** Works for services, SaaS, ecommerce and local businesses; the size unit and the
  cost logic follow the company type.

## Layout

```
CLAUDE.md                 rules + @import of the overview
AGENTS.md                 thin pointer for non-Claude runtimes
.claude/
  commands/               setup · costs · icp · price-it · competitors · product · prospects
                          set-engine · set-mail · mailbox · campaign · outreach · mail-sync
                          adjust-tone · calendar-sync · client · diagnose · propose · export
  templates/client/       case · sources · transcript · summary · diagnosis · questions ·
                          the four proposal types (tracked)
  skills/company-blueprint/
    SKILL.md              which file answers which need; read-only rules
    templates/            00-08 + tone + signature + offering/{unit,icp,...} placeholders (tracked)
    0*.md                 populated company-level files and indexes (gitignored)
    offering/<slug>/      populated per-unit files (gitignored); _shared/ for group ICPs
    signatures/<slug>.*   populated signatures (gitignored)
    tone/<slug>.md        how each signer writes, and why (gitignored)
tools/                    imap_fetch.py · linkedin.py · peek.py · transcribe.py · id7.py
                          code only where an agent cannot reach
documents/                source material about the company (gitignored)
clients/<slug>/           one client case: dossier, material, transcripts, summaries, emails,
                          diagnosis, proposals (gitignored)
```

The blueprint is gitignored, so a fresh clone has the framework and none of the company
knowledge. `/export` is what carries it across, and it refuses to carry the keys.

## Build order

`/setup` → `/costs` → `/icp` → `/competitors` → `/price-it`. Then the outreach side:
`/set-engine` → `/set-mail` → `/prospects` → `/campaign` → `/outreach` → `/mail-sync`.
Client work (`/client` → `/diagnose` → `/propose`) only needs `/setup` and `/price-it`.
